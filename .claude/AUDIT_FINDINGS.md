# Astral Sorcery Port — Audit Findings

**Audit started:** 2026-06-03  
**Port files:** 906 Java files (vs 1,319 in 1.16 reference)  
**Target:** Forge 1.20.1 (47.3.0), Java 17  

**Severity scale:**
- `[CRIT]` — Will cause crashes, data corruption, or silent wrong behavior
- `[HIGH]` — Functionally broken, missing feature, or wrong behavior under normal play  
- `[MED]`  — Degraded experience, incorrect API use, logic bug with narrow trigger
- `[LOW]`  — Code quality, null safety, wrong pattern, future maintenance hazard
- `[WARN]` — Suppressible warning that needs a targeted fix, dead code, style

## SYSTEM 1: Build / Configuration

### build.gradle
- `[LOW]` `gradle.properties`: `org.gradle.daemon=false` disables the daemon globally — builds will be slower in development. Intentional? If so, fine. But unusual for a mod project.
- `[LOW]` `mods.toml`: JEI is listed as a compile/runtime dependency in `build.gradle` but there is NO `[[dependencies.astralsorcery]]` entry for JEI in `mods.toml`. If JEI is installed at runtime and the game launches, this works, but the formal dependency declaration is missing. Players/pack devs won't see JEI listed as optional in the dependency list.
- `[LOW]` `mods.toml`: `logoFile="astralsorcery.png"` — this file must exist in the JAR root or `META-INF/`. Not in `src/main/resources/` — will log a warning on load (harmless but messy).
- `[LOW]` `mods.toml`: No `displayTest` field. For a client+server mod, Forge defaults to `MATCH_VERSION`. That's correct here, but worth being explicit.
- `[LOW]` `mods.toml`: description is fine but ends with `Ported to 1.20.1 Forge.` — original author attribution should be preserved as primary, port credit secondary.

### astralsorcery.mixins.json
- ✅ All 9 mixin classes verified present: `MixinCooldownTracker`, `MixinEnchantmentHelper`, `MixinEntity`, `MixinItemStack`, `MixinLivingEntity`, `MixinWorld`, `MixinClientWorld`, `ServerItemCooldownsAccessor`, `LevelSkyDarkenAccessor`.
- `[LOW]` `"required": true` — if any mixin fails to apply, the game hard-crashes. For purely aesthetic/enhancement mixins this should be `false`. All current mixins are gameplay-critical (dynamic enchantments, collision, sky darkening, cooldown events), so `required: true` is defensible, but it should be a conscious choice.
- `[WARN]` `astralsorcery.refmap.json` is checked in to `src/main/resources/` — this is a build artifact and should NOT be committed; it's regenerated by the annotation processor. Committing a stale version can cause mixin injection failures at runtime if mappings drift.

### AstralSorcery.java
- `[MED]` `@SuppressWarnings("null")` is on the whole class — this suppresses ALL null warnings, hiding real issues. The only actual `@Nonnull` concern is `instance` and `modContainer` being potentially null before the constructor runs (i.e., during the static field initializer). The correct fix is `@Nonnull` field annotations with explicit `Objects.requireNonNull` in `getInstance()`, not a blanket class-level suppression.
- `[LOW]` `modContainer = ModList.get().getModContainerById(MODID).orElseThrow()` — `orElseThrow()` throws `NoSuchElementException` with no message. Should be `.orElseThrow(() -> new IllegalStateException("AstralSorcery mod container not found"))` for debuggability.
- `[LOW]` `DistExecutor.unsafeRunForDist` is deprecated in Forge 47.x in favor of safe alternatives. Forge recommends `DistExecutor.safeRunForDist` with `() -> ClassName::new` form, or direct constructor calls guarded by `@OnlyIn`. The `unsafe` variant bypasses class loading checks.

### AstralSorcery.java (continued)

### CommonProxy.java
- `[LOW]` Inline lambdas directly in `attachEventHandlers` for `TimeStopController` cleanup: `forgeBus.addListener((net.minecraftforge.event.level.LevelEvent.Unload e) -> { if (!e.getLevel().isClientSide()) ... })`. This is valid in Forge but means those classes have zero per-instance state. Fine as-is, but note that Forge handles `@SubscribeEvent` static methods via class registration.

### ClientProxy.java  
- `[MED]` `onRegisterRenderers` is annotated `@SuppressWarnings("null")`. The underlying cause: `BlockEntityTypesAS.ALTAR.get()` returns `@Nullable` per Forge's type annotation on `RegistryObject.get()`. Correct fix is `Objects.requireNonNull(BlockEntityTypesAS.ALTAR.get(), "ALTAR BET not registered")` on any `.get()` call that feeds into non-null API, rather than suppressing the whole method.
- `[LOW]` `ItemProperties.register(ItemsAS.RESONATOR.get(), new ResourceLocation("upgrade"), ...)` — `new ResourceLocation("upgrade")` creates `minecraft:upgrade` (the `ResourceLocation(String)` constructor with no `:` uses `minecraft` as namespace). Should be `AstralSorcery.key("upgrade")` → `astralsorcery:upgrade`. Also requires updating the resonator model JSON's predicate key to match.
- `[LOW]` `@SuppressWarnings("null")` on `onRegisterLayerDefinitions`, `onRegisterOverlays`, `onClientSetup`, `onRegisterReloadListeners` — all stem from the same `RegistryObject.get()` nullability issue. Fix at the call site with `requireNonNull`, remove suppressions.
- `[LOW]` `@SuppressWarnings({"unchecked", "null"})` on `onAddLayers` — the `unchecked` is legitimate (double cast needed for Forge's generic renderer API). The `null` suppression for `event.getSkin(skin)` is already guarded by `if (renderer != null)`. The `null` warning suppression is therefore redundant once the `RegistryObject.get()` issue is fixed elsewhere. Keep `unchecked`; remove `null`.

### BlockEntitySynchronized.java (BASE CLASS — AFFECTS ALL TEs)
- `[HIGH]` `handleUpdateTag(CompoundTag tag)` calls `super.handleUpdateTag(tag)`, which in vanilla 1.20.1 calls `load(tag)`. Our `load()` override calls BOTH `readCustomNBT(tag)` AND `readSaveNBT(tag)`. The update tag (from `getUpdateTag()`) only contains `writeCustomNBT` data — it does NOT contain the disk-only fields written by `writeSaveNBT`. Therefore, every time the client receives a chunk/BE update, `readSaveNBT(tag)` runs on an incomplete tag, silently resetting ALL disk-only fields to their zero/null/false defaults. This affects ALL block entities that store data in `readSaveNBT`. Fix: remove `super.handleUpdateTag(tag)` call and call only `readCustomNBT(tag)`.
  ```java
  // WRONG (current):
  public void handleUpdateTag(CompoundTag tag) {
      super.handleUpdateTag(tag); // calls load() → reads both custom AND save NBT with incomplete data
      readCustomNBT(tag);         // readCustomNBT called twice
  }
  // CORRECT:
  public void handleUpdateTag(CompoundTag tag) {
      readCustomNBT(tag);  // only read what was written to the update tag
  }
  ```
- `[MED]` As a consequence of the above: `BlockEntityAltar.readSaveNBT()` will zero-out `storedStarlight`, `recipeTick`, `isCrafting`, `starlightCapacity`, `receivedConstellation`, and `activeRecipeId` on every client sync update. The altar GUI starlight meter will always show empty from the client's perspective.
- `[LOW]` `static final Random rand` in base class is a shared mutable field — not thread-safe. Should use `level.getRandom()` at call sites instead. Harmless in single-threaded world tick context but is bad practice.

### BlockEntityAltar.java  
- `[MED]` `storedStarlight`, `isCrafting`, `recipeTick`, `receivedConstellation`, and `activeRecipeId` are in `readSaveNBT`/`writeSaveNBT` (disk only), but NOT in `readCustomNBT`/`writeCustomNBT` or `readNetNBT`/`writeNetNBT`. These fields are never sent to the client. The GUI cannot show the current starlight level or crafting state unless `ContainerData` in the container handles the sync. Must verify `ContainerAltarDiscovery` and sibling containers use `ContainerData` for these values.
- `[MED]` `structureValid` field exists, has getter/setter, and is serialized in NBT — but is never set to `true` anywhere in this class. The comment says "Port has no multiblock structure requirement". Dead state. Either remove it entirely or track it properly if multiblock is eventually re-added.
- `[LOW]` `completeCrafting()` calls `ResearchManager.informCraftedAltar(sp, AltarType.DISCOVERY)` always — should use `completedRecipe.getAltarType()` to grant tier-appropriate progression.
- `[LOW]` `getDisplayName()` returns generic `"block.astralsorcery.altar"` for all tiers. Consider tier-specific names like `"block.astralsorcery.altar_discovery"` for better GUI titles.
- `[LOW]` `@SuppressWarnings("null")` on `getDisplayName()` — `Component.translatable()` is `@Nonnull`. The suppression is targeting the `@Nonnull` return annotation, likely because the IDE can't verify `Component.translatable` is non-null. Remove suppression and add explicit `Objects.requireNonNull` wrapper or verify the annotation.
- `[LOW]` `doesSeeSky()` is called but defined in the base class — need to verify it exists and is correct. (Verify in `BlockEntityTick`.)
- `[LOW]` `gatherSkyStarlight()` height formula `Math.pow(getBlockPos().getY() / 7.0, 1.5) / 65.0F` uses hardcoded `7.0` and `65.0` as magic numbers. If the 1.16 formula used these values, document WHY they were chosen.

## SYSTEM 6: Tile Entities (Block Entities)

### ContainerAltarBase.java
- `[HIGH]` `getStarlightStored()` and `getStarlightCapacity()` return values from `altar.getStarlightStored()` / `altar.getStarlightCapacity()`. Since `storedStarlight` is only in `writeSaveNBT` (never synced to client), the GUI starlight meter ALWAYS reads 0 on the client. Fix: move `storedStarlight`, `starlightCapacity`, `recipeTick`, and `isCrafting` from `writeSaveNBT`/`readSaveNBT` to `writeCustomNBT`/`readCustomNBT` so they are included in chunk load and network sync. They'll be redundantly saved to disk but that's fine.
- `[MED]` No `ContainerData` / `addDataSlots()` call — there is no mechanism for continuous server→client sync of dynamic int values (progress bar, starlight level) while the menu is open. In vanilla, this is how furnace progress is synced. If the altar's starlight changes while the GUI is open, the display won't update until the next BE update packet. Should add `ContainerData` for `storedStarlight` (as scaled int), `recipeTick`, and `isCrafting` to support live GUI updates.
- `[MED]` `ContainerLevelAccess.create(altar.getLevel(), ...)` — `altar.getLevel()` is `@Nullable`. Called in the constructor, which runs both server-side (in `createMenu()`) and client-side (in `fromNetwork()`). On the client, `altar.getLevel()` should be non-null for an already-placed BE, but it's not null-checked. Should be guarded.

### BlockEntityTick.java
- `[LOW]` `ticksOnClient()` and `ticksOnServer()` methods are never consulted in `tickStatic()` or any tick dispatcher. These methods are dead API — subclasses overriding them won't achieve the expected behavior. Remove or implement the flags check in tick dispatching.

### BlockEntityGateway.java
- `[LOW]` Has its own `ticksExisted` counter that duplicates `BlockEntityTick.tickCount`. Use `super.getTicksExisted()` from the base class and remove the local field.
- `[LOW]` `readSaveNBT`/`writeSaveNBT` are overridden with empty bodies (just `super.xxx()`) — unnecessary boilerplate; delete them.
- `[LOW]` `validateStructure()` checks that 4 cardinal positions at distance 2 are non-air. Very loose check — any block qualifies. In 1.16, was this marble pillars specifically? Should at least check for an AS marble block tag. If intentionally loose, document why.

### PktSyncBlockEntity.java
- ✅ Correctly calls `readCustomNBT` + `readNetNBT` on the client — does NOT call `readSaveNBT`. Safe for partial sync.
- `[LOW]` Uses `DistExecutor.unsafeRunWhenOn(Dist.CLIENT, ...)` which is deprecated in Forge 47.x for the same reasons as `unsafeRunForDist`. Should use `DistExecutor.safeRunWhenOn`.

### BlockEntitySynchronized.java (HIGH SEVERITY — revisited)
- `[HIGH]` `handleUpdateTag()` issue confirmed: the initial chunk-load sync (via `handleUpdateTag`) calls `super.handleUpdateTag(tag)` → `load(tag)` → `readSaveNBT(tag)` with an incomplete tag (update tag contains only `writeCustomNBT` fields). This resets ALL disk-only fields to defaults on initial load. For `BlockEntityAltar`, this means `storedStarlight → 0`, `isCrafting → false`, `recipeTick → 0` on the client's first view of the altar.
  - **Fix**: Override `handleUpdateTag()` to skip `super` call:
  ```java
  @Override
  public void handleUpdateTag(@Nonnull CompoundTag tag) {
      readCustomNBT(tag);
      // Do NOT call super — vanilla calls load() which also runs readSaveNBT
      // with an incomplete update tag, zeroing disk-only fields client-side.
  }
  ```
